# Запросы Android-клиента к backend

Статус: **предложение для согласования с Денисом**, не описание реализованного API. Маршруты, названия полей и формат ошибок нужно утвердить в OpenAPI до подключения сети. Базовый путь `/api/v1` ниже также предложен, а не подтверждён.

Сейчас `FakeKanbanRepository` возвращает демонстрационные данные, изменения задач и команды живут в памяти, а созданные события и типы событий — в `SharedPreferences`. Для синхронизации пользователей и устройств сервер должен стать источником этих данных.

## Общие правила контракта

- Все запросы, кроме входа и обновления токена: `Authorization: Bearer <accessToken>`.
- JSON в `UTF-8`; идентификаторы — стабильные числовые или строковые ID, но один формат во всех ответах. Не связывать сущности по имени пользователя.
- Даты — `YYYY-MM-DD`, моменты времени — ISO 8601 с часовым поясом, например `2026-10-23T18:00:00+03:00`. Сервер возвращает оба конца события; Android сам форматирует их для показа.
- Для списков определить `limit`, `cursor`/`offset`, порядок сортировки и признак следующей страницы. Пустой список — `200` с `items: []`, не `404`.
- Для ошибок нужен единый объект, например `{"code":"FORBIDDEN","message":"Нет доступа","details":{}}`; согласовать `400`, `401`, `403`, `404`, `409`, `422` и ошибки сети.
- На сервере проверять членство в команде, роль, принадлежность проекта команде, владельца личного события и учебную группу. Скрытая кнопка в Android не является проверкой прав.

## P0 — запросы, без которых нельзя заменить mock-данные

### 1. Вход и текущий пользователь

| Запрос | Что нужно Android | Минимальный ответ |
|---|---|---|
| `POST /auth/login` | `{"login":"samir","password":"..."}` | `accessToken`, срок действия, `refreshToken` (если используется), `user` |
| `POST /auth/refresh` | Обновление истёкшего access token; точное тело согласовать | Новая пара токенов/новый access token |
| `POST /auth/logout` | Завершение сессии, если refresh token отзывается сервером | `204` |
| `GET /users/me` | Восстановить профиль после перезапуска | `id`, `name`, `login`, `active`, `position`, `studentGroup`, членства/роли |

Роль лучше возвращать **в членстве конкретной команды**, например `memberships: [{"teamId":1,"role":"LEAD"}]`: один человек может быть тимлидом в одной команде и участником в другой. Нужно подтвердить, поддерживает ли это backend. Пароль никогда не возвращать.

### 2. Команды, участники, проекты

| Запрос | Назначение | Важные поля ответа |
|---|---|---|
| `GET /teams` | Список доступных пользователю команд для экрана выбора | `id`, `name`, `description`, `isMember`, `myRole`, `memberCount` |
| `GET /teams/{teamId}` | Детали выбранной команды | Те же поля и правила вступления |
| `GET /teams/{teamId}/members` | Список участников и переход в профиль | `userId`, `name`, `position`, `role`, `active` |
| `POST /teams/{teamId}/members/me` | Вступить в команду, если разрешено | Обновлённое членство; ошибка `403/409` при запрете |
| `DELETE /teams/{teamId}/members/me` | Выйти из команды | `204`; правила для последнего тимлида уточнить |
| `GET /teams/{teamId}/projects` | Проекты **только этой команды** для переключателя доски | `id`, `teamId`, `name`, `description?`, `archived?` |

Выбор активной команды/проекта может оставаться локальным UI-состоянием; серверу нужны их ID в последующих запросах. После смены команды Android заново запрашивает её проекты, доску, участников и события.

### 3. Доска, задачи, история

| Запрос | Назначение | Минимальный контракт |
|---|---|---|
| `GET /projects/{projectId}/board` | Колонки доски | `boardId`, `projectId`, `columns: [{id, code, title, position}]` |
| `GET /projects/{projectId}/tasks?limit=...&cursor=...` | Карточки выбранного проекта | `id`, `projectId`, `teamId`, `boardColumnId`, `status/code`, `position`, `title`, `description`, `assigneeId`, `priority`, `dueDate`, `completedAt` |
| `GET /tasks/{taskId}` | Детали задачи | Поля карточки + `attachments`, `resultAttachments`, `comments` либо ссылки на отдельные списки |
| `POST /projects/{projectId}/tasks` | Создать задачу | В теле `title`, `description`, `assigneeId`, `dueDate`, `priority?`; в ответе созданная задача с серверным ID |
| `PATCH /tasks/{taskId}/status` | Переместить задачу | В теле `boardColumnId`/`status` и, если нужно, `position`; в ответе обновлённая задача |
| `GET /teams/{teamId}/tasks?status=DONE&completedFrom=...&completedTo=...` | История команды по периоду | Задачи с `completedAt`, исполнителем и результатом; пагинация |
| `POST /tasks/{taskId}/comments` | Отправить комментарий | В теле `text`; в ответе `id`, `authorId`, `text`, `createdAt` |

Сервер должен валидировать переходы: исполнитель `WAITING → WORKING → CHECKING`, тимлид `CHECKING → DONE/WORKING` и `DONE → WORKING`, если такие правила утверждены. Чужой участник получает `403`, конфликт устаревшего статуса — `409`. Уточнить, статусы фиксированные или определяются `Board_Column`; Android сейчас использует четыре фиксированных статуса.

### 4. Единое расписание и события

| Запрос | Назначение | Минимальный контракт |
|---|---|---|
| `GET /schedule/lessons?group=203&from=2026-10-23&to=2026-10-30` | Пары выбранной учебной группы | `id`, `startsAt`, `endsAt`, `title`, `room`, `teacher`, `kind` (`LECTURE/PRACTICE/LAB`), `updatedAt`, `sourceStatus` |
| `GET /events?teamId=1&group=203&from=...&to=...` | Все **доступные текущему пользователю** командные, групповые и личные события | Список `Event` ниже; сервер сам фильтрует видимость |
| `GET /events/{eventId}` | Открыть описание из ленты | Полный `Event` или `403/404` при отсутствии доступа |
| `POST /events` | Создать событие | В теле название, описание, время начала/окончания, тип, видимость, адресат и интервалы напоминаний; ответ `201` с `Event` |
| `GET /event-types` | Базовые и доступные пользовательские типы | `id`, `title`, `color`, `scope`, `defaultReminderMinutes` |
| `POST /event-types` | Создать свой тип отдельной кнопкой | `title`, `color`, `scope`, `defaultReminderMinutes`; ответ `201` с созданным типом |

Пример предлагаемого тела `POST /events`:

```json
{
  "title": "Созвон команды",
  "description": "Обсудить итоги спринта",
  "startsAt": "2026-10-24T18:00:00+03:00",
  "endsAt": "2026-10-24T19:00:00+03:00",
  "visibility": "TEAM",
  "teamId": 1,
  "group": null,
  "typeId": "meeting",
  "reminderMinutes": [60, 30]
}
```

Пример нужного ответа `Event`: тот же набор полей плюс `id`, `ownerId`, `createdAt`, `updatedAt`. Для `GROUP` должен быть заполнен адресат `group`, для `PERSONAL` владелец определяется токеном, а не доверенным `ownerId` из тела. Уточнить, кто вправе создавать событие для всей команды/группы и можно ли указывать окончание на следующий день.

После успешного `POST` другой участник должен получить командное или групповое событие обычным `GET /events`; запись только в локальное хранилище одного телефона не подходит. Пары из ИСУ желательно отдавать с `sourceStatus`/временем последнего успешного обновления, чтобы приложение могло показать кеш при сбое источника.

### 5. Публичный профиль участника

`GET /users/{userId}` — `id`, `name`, `position`, допустимые к показу данные и статистика (`inProgress`, `completed`, `total` либо отдельный `GET /users/{id}/stats?teamId=...`). Переход в профиль должен работать из списка команды, карточки задачи и истории; Android возвращается назад на предыдущий экран локальной навигацией, отдельный API для этого не нужен.

## P1 — запросы для уже показанных действий и следующей интеграции

| Запрос | Для чего |
|---|---|
| `PATCH /teams/{teamId}` | Тимлид меняет название/описание команды |
| `POST /teams/{teamId}/members` | Тимлид создаёт/приглашает участника; **способ выдачи временного пароля согласовать отдельно**, не возвращать пароль в общем списке |
| `PATCH /teams/{teamId}/members/{userId}` | Изменить роль/заблокировать или восстановить доступ в команде |
| `GET /tasks/{taskId}/attachments` | Показать исходные файлы и результаты работы |
| `POST /tasks/{taskId}/attachments` | Загрузить файл/результат; договориться о `multipart/form-data` или предварительно подписанном URL |
| `GET /attachments/{attachmentId}/download` | Получить файл по авторизованному запросу или короткоживущей ссылке |
| `PATCH /users/me` | Сохранить учебную группу в аккаунте, чтобы расписание совпадало на разных устройствах |
| `PATCH /events/{eventId}`, `DELETE /events/{eventId}` | Редактирование и удаление события, когда эти действия появятся в UI |

Тема оформления может остаться локальной настройкой Android и не требует API. Локальные напоминания через `AlarmManager` также не требуют FCM. Если нужны удалённые push или синхронизация настроек уведомлений между устройствами, отдельно согласовать регистрацию FCM-токена и ответственного за планирование уведомлений; не отправлять одни и те же напоминания двумя способами.

## Что нужно получить от backend-разработчика

1. OpenAPI-файл или Swagger с примерами успешных и ошибочных ответов для P0.
2. Адрес dev-сервера, тестовые аккаунты тимлида и участника, правила выдачи/обновления токенов.
3. Решение по ролям (глобальные или в команде), вступлению в команду, видимости событий, типам событий и фиксированным/настраиваемым колонкам.
4. Реальные значения enum, формат времени и ошибок, пагинацию, ограничения на размер файлов.
5. Состояние реализации каждого endpoint: готов, в работе, не запланирован. До готовности API Android продолжит использовать mock-данные.

После согласования этого файла нужно привести DTO Android к фактическому OpenAPI, не подгоняя серверный контракт под текущие `String`-поля демонстрационных моделей.
