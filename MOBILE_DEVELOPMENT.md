# Документация разработчика мобильного приложения

## 1. Назначение

`mobile/` — Android-клиент Kanban Board. На Sprint 0 приложение демонстрирует основной пользовательский путь на локальных данных и задаёт основу для интеграции с backend.

Технологии:

- Kotlin;
- Jetpack Compose + Material 3;
- Navigation Compose;
- Android ViewModel;
- Gradle Kotlin DSL;
- минимальная версия Android — API 26;
- compile/target SDK — API 37;
- JDK 17.

## 2. Структура

```text
mobile/
├── app/src/main/java/com/kanbanboard/mobile/
│   ├── MainActivity.kt           # точка входа Android
│   ├── data/
│   │   └── KanbanRepository.kt   # контракт данных и mock-реализация
│   ├── model/
│   │   └── Models.kt             # модели предметной области
│   └── ui/
│       ├── AppViewModel.kt       # состояние и действия пользователя
│       ├── KanbanApp.kt          # навигация и экраны
│       └── theme/Theme.kt        # дизайн-токены приложения
└── app/src/test/                 # локальные unit-тесты
```

Направление зависимостей: `UI -> ViewModel -> KanbanRepository -> источник данных`. UI не должен напрямую обращаться к сети или базе данных.

## 3. Экраны и сценарии

### Вход

Экран повторяет веб-клиент: логин и пароль, выданные тимлидом. Mock-аккаунты: `alexey / lead123` для тимлида и `maria / member123` для участника. После подключения backend метод `KanbanRepository.login` должен возвращать профиль сервера или ошибку авторизации.

### Доска

Поддерживаются статусы `WAITING`, `WORKING`, `CHECKING`, `DONE`. Переход вперёд выполняется из деталей задачи. При подключении backend мутация должна отправляться на сервер, а локальное состояние — обновляться после успешного ответа.

### Детали задачи

Отображаются описание, исполнитель, дедлайн, исходные файлы и комментарии. Сейчас добавление комментария и смена статуса живут только в памяти процесса.

### История задач

Показывает выполненные задачи, результат работы, дату завершения и исполнителя. Доступны поиск и фильтрация по участнику.

### Участники и управление командой

Список участников и публичный профиль доступны всей команде. Профиль показывает роль, статус доступа и статистику задач. Тимлид дополнительно может открыть управление командой, изменить её описание, создать mock-аккаунт и заблокировать или восстановить участника.

### Профиль

Содержит те же основные данные и статистику, что веб-версия. Расписание и события открываются из профиля как дополнительные возможности и не заменяют основные разделы сайта.

### Расписание

Предусмотрены группы 203 и 204. Локальные данные имитируют fallback-режим ИСУ. В production репозиторий должен:

1. запросить свежие данные;
2. сохранить их локально;
3. при ошибке сети вернуть последний кеш с отметкой времени обновления.

### События

Поддержаны три уровня видимости: команда, группа, личное. Сценарии напоминаний показаны в карточках, но системные уведомления пока не планируются и не создаются.

## 4. Соответствие дизайну веб-клиента

Мобильная тема повторяет токены ветки `frontend-new-design`:

| Токен | Значение | Назначение |
|---|---:|---|
| Background | `#F5F7FB` | фон экранов |
| Surface | `#FFFFFF` | карточки и навигация |
| Text | `#20242C` | основной текст |
| Muted | `#77808F` | вторичный текст |
| Primary | `#6576DF` | основные действия и активные состояния |
| Border | `#E5E9F0` | границы |
| Danger | `#C65F68` | ошибки и опасные действия |

Основные карточки имеют радиус 14 dp, крупные контейнеры — 22 dp. Новые компоненты должны использовать цвета из `ui/theme/Theme.kt`, а не объявлять отдельные основные цвета внутри экранов.

## 5. Подключение backend

Необходимо сохранить интерфейс `KanbanRepository` и заменить `FakeKanbanRepository` реализацией `RemoteKanbanRepository`. Рекомендуемый порядок:

1. согласовать OpenAPI-контракт с backend-разработчиком;
2. добавить DTO отдельно от UI-моделей;
3. реализовать преобразование DTO -> model;
4. обрабатывать loading/error/empty состояния в `AppUiState`;
5. вынести кеш расписания и сессию пользователя в отдельные локальные источники данных;
6. добавить dependency injection только когда появятся минимум две реальные реализации зависимостей.

Предполагаемые группы endpoint'ов:

```text
POST  /auth/login
GET   /tasks
PATCH /tasks/{id}/status
POST  /tasks/{id}/comments
POST  /tasks/{id}/attachments
GET   /schedule?group=203
GET   /events
```

Это предварительный контракт, не основание для backend-реализации без согласования.

## 6. Проверки перед Pull Request

```powershell
cd mobile
.\gradlew.bat test assembleDebug
```

Дополнительно вручную проверить:

- неверная пара логин/пароль показывает ошибку;
- `alexey / lead123` открывает функции тимлида;
- `maria / member123` открывает функции участника без управления командой;
- фильтры статусов показывают правильные карточки;
- история показывает только выполненные задачи;
- открываются список участников и профиль участника;
- тимлид может открыть управление командой и создать задачу;
- статус задачи изменяется;
- новый комментарий появляется в списке;
- переключаются группы 203/204;
- фильтруются типы событий;
- выход возвращает на экран входа.

## 7. Git-процесс

- базовая ветка: `develop`;
- текущая feature-ветка: `mobile-app-template`;
- прямые изменения в `develop` не допускаются;
- небольшие логические изменения оформляются отдельными коммитами;
- Pull Request создаётся из `mobile-app-template` в `develop`;
- перед слиянием обязательны сборка, тесты и review другим участником.

4. Добавить создание и редактирование событий.
5. Реализовать уведомления через WorkManager/AlarmManager после согласования требований.
6. Вынести Wear OS-клиент в отдельный Gradle-модуль после стабилизации API расписания.
