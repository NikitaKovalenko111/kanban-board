# План контейнеризации и автоматического деплоя

## Уточнённая область работы

Сервер будет находиться на компьютере другого человека. Текущая задача пользователя — подготовить Docker-образы, Compose и материалы для передачи. Локальная сборка и проверка контейнеров выполнены; инструкция владельцу сервера — `docs/handoff.md`. Настройка чужого сервера и его доступов остаётся владельцу сервера. Готовые образы не экспортировались в архивы и не публиковались в registry; основной подготовленный способ передачи — исходники и сборка через Compose на целевом компьютере.

## Этапы и критерии готовности

1. Проверить существующий CI/CD и подготовить настройку SSH и GitHub Secrets.
   Результат: список секретов, схема доступа, выявленные ограничения и инструкция для администратора.
   Аудит выполнен; установка ключа на сервер и заполнение GitHub Secrets ещё не выполнены.
2. Создать `backend/Dockerfile`, `client/Dockerfile`, `.dockerignore` для обоих контекстов и корневой `compose.yaml`.
   Учесть Go 1.25.3, сборку React/Vite, раздачу SPA, PostgreSQL, постоянный том БД и конфигурацию через окружение.
   Критерий: обе сборки проходят, `docker compose config` проходит, контейнеры запускаются, `/health` и страницы приложения доступны.
   Выполнено локально: результаты в `docs/docker.md`.
3. Подготовить сервер и завершить SSH-доступ.
   **НЕ ВЫПОЛНЕН. Пропущен по просьбе пользователя: SSH не отвечает до авторизации.**
   Проверить адрес, порт 2222, пользователя, Docker Compose, каталог проекта, доступ сервера к GitHub и конфигурацию БД.
   Установить публичный ключ и заполнить четыре GitHub Secrets. Секреты не коммитить.
4. Доработать CD после успешной локальной сборки.
   Доставлять точный SHA успешного CI, исключить одновременные деплои, добавить проверку здоровья и план отката.
   Реализация подготовлена локально: `.github/workflows/cd.yaml`, `scripts/deploy.sh`; настройка и откат описаны в `docs/cd.md`. Запуск на сервере зависит от невыполненного этапа 3.
5. Проверить полный деплой через push в main.
   **НЕ ВЫПОЛНЕН: зависит от пропущенного этапа 3.** Изменения Docker/CD пока локальные, в GitHub не отправлены. Подготовлена серверная проверка `scripts/verify-deploy.sh`; полный прогон, сохранность данных и откат на сервере ещё не проверены.
   Сопоставить SHA успешного CI с SHA на сервере, проверить контейнеры, логи, HTTP и сохранность данных после перезапуска.
   Зафиксировать результаты и команду отката на предыдущую проверенную версию.

## Секреты, которые ожидает текущий CD

| Имя | Значение | Как подготовить |
| --- | --- | --- |
| `SERVER_HOST` | IP или DNS сервера, без схемы и порта | Получить у администратора |
| `SERVER_USER` | Пользователь для деплоя | Получить у администратора |
| `SERVER_SSH_KEY` | Полный приватный ключ отдельной пары для GitHub Actions, включая BEGIN/END и переносы строк | Создать пару, публичную часть установить в authorized_keys этого пользователя |
| `SERVER_KNOWN_HOSTS` | Запись known_hosts для `[HOST]:2222` | Получить ключ хоста и сверить отпечаток через доверенный канал |

SHA коммита, отпечаток SSH-ключа и приватный SSH-ключ — разные значения. В `SERVER_SSH_KEY` нужен именно приватный ключ, а не SHA и не `.pub`.

## Инструкция для администратора / Никиты

1. Подтвердить HOST, USER, порт 2222 и каталог проекта. Не пересылать существующий личный приватный ключ сервера.
2. На доверенном компьютере создать отдельную пару для этого деплоя:

   ```sh
   ssh-keygen -t ed25519 -C "github-actions-kanban-deploy" -f ./kanban-deploy
   ```

   Для текущего неинтерактивного workflow оставить passphrase пустой. Не создавать файлы внутри репозитория. Приватный файл `kanban-deploy` хранить только в защищённом месте.
3. Добавить содержимое `kanban-deploy.pub` в `~/.ssh/authorized_keys` серверного пользователя. На Linux установить права 700 для `~/.ssh` и 600 для `authorized_keys`. Убедиться, что владелец — нужный пользователь.
4. Получить запись ключа хоста:

   ```sh
   ssh-keyscan -p 2222 -t ed25519 HOST > server_known_hosts
   ssh-keygen -lf server_known_hosts
   ```

   `ssh-keyscan` сам по себе не подтверждает подлинность сервера. Сверить отпечаток с результатом `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` через консоль сервера или администратора.
5. Проверить подключение с новой парой и проверенным known_hosts:

   ```sh
   ssh -p 2222 -i ./kanban-deploy -o IdentitiesOnly=yes -o BatchMode=yes -o StrictHostKeyChecking=yes -o UserKnownHostsFile=./server_known_hosts USER@HOST 'whoami; docker compose version'
   ```

6. В GitHub открыть репозиторий → Settings → Secrets and variables → Actions → New repository secret. Добавить четыре значения из таблицы. Приватный ключ вставить целиком с переносами строк. Не отправлять его в чат, issue или коммит.
7. Отдельно проверить доступ сервера к GitHub: он нужен для `git pull` и не предоставляется автоматически ключом GitHub Actions → сервер. Если репозиторий закрытый, настроить отдельный read-only deploy key для сервер → GitHub.
