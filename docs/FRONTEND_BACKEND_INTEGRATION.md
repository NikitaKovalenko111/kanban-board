# Интеграция frontend с обновлённым backend

Обновлено **5 ноября 2026 года**. Ветка: `frontend-backend-integration`, исходный коммит backend: `f270f0e`.

Этот отчёт заменяет выводы предыдущей проверки от 4 ноября: бизнес-API теперь существует, прежние утверждения об отсутствии задач, проектов, пользователей, расписания и файлов больше не актуальны.

Изменены только client/ и этот отчёт в корневом docs/. Backend, mobile, корневой Compose, CI/CD и deployment-скрипты не изменялись.

## Дополнительная проверка ошибок 5 ноября

### Расписание: GET /api/v1/events возвращает 500 — ошибка backend

Подтверждено сопоставлением предоставленного лога `SQLSTATE 42P18: could not determine data type of parameter $1` с текущим кодом [ListEvents](../backend/internal/storage/repositories/event/repository.go#L114).

В `QueryContext` передаются пять аргументов: `userID, personID, groupList, from, to`. SQL использует `$2`, `$3`, `$4`, `$5`, но нигде не использует `$1`. PostgreSQL не может определить тип первого параметра. Поэтому корректный запрос клиента с датами, UUID участника и группами также завершается ошибкой; изменение фильтров интерфейса эту причину не устраняет.

Нужно исправление на стороне backend: убрать неиспользуемый аргумент `userID` именно из SQL-вызова и последовательно перенумеровать параметры ($2 → $1, $3 → $2, $4 → $3, $5 → $4). Сам `userID` остаётся нужен функции для применения приватности после чтения событий. Затем повторить GET /events под капитаном и участником, включая просмотр чужого расписания с проверкой приватности. Backend в рамках этой проверки не изменялся. Клиент продолжает показывать ошибку загрузки, не подменяя её пустым расписанием.

### Создатель проекта не входит в участников — исправлено в client

Ранее POST /projects отправлял только `name` и `description`. Backend сохраняет авторство отдельно и добавляет в `project_members` только записи из входного `members` ([CreateProject](../backend/internal/storage/repositories/project/repository.go#L142)). Авторство не равно членству.

Теперь клиент в том же POST передаёт `members: [{ userId: <UUID текущей сессии>, role: "Тимлид" }]`. Создание проекта и начального членства выполняет существующая серверная транзакция. Эта роль относится к проекту и не меняет глобальную роль CAPTAIN. Исправление применяется к новым проектам; для уже созданных капитана нужно добавить через управление участниками проекта. Автоматическая миграция старых данных не выполнялась.

### Назначение исполнителя: Bad Request / некорректный UUID — исправлено в client

В форме изменения исполнителя существующей задачи оставалось `Number(assigneeValue)`. Для UUID результат — `NaN`; адаптер преобразовывал его в строку `"NaN"`, которую сервер закономерно отклонял. При первоначальном создании задачи UUID уже обрабатывался правильно.

Теперь форма сохраняет UUID строкой в backend-режиме, числовые идентификаторы остаются только для mock-режима. Снятие назначения передаёт `null`. Регрессионные тесты проверяют выбор исполнителя в форме, снятие назначения и строковый `assigneeId` в PATCH /tasks/:id.

В этой дополнительной проверке использованы исходный код, предоставленный серверный лог и автоматические клиентские тесты. Новые аккаунты и проекты в рабочей БД не создавались; повторная живая проверка расписания требует исправления SQL на сервере.

## Контракт и подключённые разделы

Источники: [API backend](../backend/docs/API.md), [OpenAPI](../backend/docs/openapi.yaml), [роутер](../backend/internal/transport/http/http.go), [модели ответа](../backend/internal/models/repo_models.go). Подтверждено запуском текущего неизменённого backend с отдельными PostgreSQL и MinIO.

База HTTP API — **/api/v1**. Идентификаторы — UUID, время записи — RFC3339. Защищённые запросы используют Authorization: Bearer. Ошибка: `{error:{code,message,fields?}}`. Неизвестные поля запроса отклоняются сервером, поэтому mock-поля не передаются напрямую.

## Подтверждённые ошибки и расхождения backend

### Выход и смена пароля: обработчики перекрыты публичным роутером

[StartPublic/StartProtected](../backend/internal/transport/http/handlers/auth/handler.go) регистрируют login/refresh в отдельном authRouter, logout/change-password — в общем защищённом apiRouter. Но более длинный маршрут /api/v1/auth/ в [главном роутере](../backend/internal/transport/http/http.go) направляет **все** auth-запросы в публичный authRouter, где двух защищённых обработчиков нет.

На реальном сервере:
- POST /api/v1/auth/logout с корректными Bearer и refreshToken → **404**.
- POST /api/v1/auth/change-password с корректным Bearer и телом → **404**.
- Refresh после неуспешного logout остаётся действующим: серверный отзыв не произошёл.

Frontend отправляет правильный camelCase payload и Bearer. При выходе очищает sessionStorage, Redux и связанные данные аккаунта; показывает, что локальный выход выполнен, но сервер не подтвердил завершение сессии. Смена пароля показывает ошибку, а не ложный успех. Эта ошибка backend не исправлялась.

### Напоминания не образуют единую модель наследования

[Event repository](../backend/internal/storage/repositories/event/repository.go) хранит исходные напоминания события в event_reminders, а PUT /me/reminders — в user_reminders. [Генератор уведомлений](../backend/internal/storage/repositories/notification/repository.go) обрабатывает обе таблицы независимо.

Следствия:
- Изменение личного интервала **не отменяет** ранее сохранённый исходный интервал события; возможны два разных уведомления, несмотря на одно поле в вебе.
- Пустой minutes удаляет личную запись, но не отменяет исходное напоминание.
- Изменение defaultReminders типа не обновляет снимок event_reminders у существующих событий.
- GET /events и GET /events/:id не возвращают исходный снимок напоминаний; GET /me/reminders возвращает только личные записи. У клиента нет полного способа показать/заменить исходную настройку старого события.
- При создании события пустой myReminders не позволяет выразить независимое отключение, если у типа есть defaultReminders.
- Backend допускает несколько интервалов; по требованию интерфейс редактирует один и использует первый из полученного списка. Сохранение типа заменяет его список одним выбранным интервалом.

Frontend показывает предупреждение в форме личных напоминаний, отправляет/читает личную настройку и не утверждает, что отменил исходную. При создании с индивидуальным интервалом сохраняется тот же личный интервал для последующего чтения; совпадающие notification keys сервер дедуплицирует. Полноценное взаимное замещение/отключение требует изменения контракта и логики backend.

Также backend принимает **1–40320 минут**. Значение 0 «в момент начала» отклоняется; в серверном UI оно недоступно. В mock-режиме прежнее поведение сохранено.

### События не привязаны к проекту

У Event нет projectId; POST /events его не принимает. В серверном расписании скрыт проектный переключатель, события не фильтруются вымышленным проектом. Поддержаны TEAM/GROUP/PERSONAL и группы из API. GROUP требует группу, поэтому поле появляется только для этой категории; у личных и командных событий его нет.

Отдельных категорий «Дедлайны»/«Контрольные точки» в Event нет; соответствующая опция создания/фильтра скрыта в серверном режиме. Пары загружаются отдельно из /schedule/lessons. Группы не захардкожены как 203/204: используются реальные groupCode/name.

### Цвет проекта и изменение команды не предусмотрены контрактом

Project не содержит color, PATCH/POST не принимают его. В серверном режиме выбор цвета скрыт; маркеры получают стабильный презентационный цвет из UUID, не выдаваемый за сохранённый сервером.

GET /team возвращает фиксированные название/описание; PATCH /team отсутствует. Изменение команды не имитируется. Локальная настройка светлой/тёмной темы не требует API и работает.

### История содержит названия колонок

Фактические fromColumn/toColumn в TaskHistory — **названия** («Ожидает», «В работе»), а не UUID. Адаптер поддерживает названия и UUID, сохраняет исходные подписи и не ломает загрузку доски при старом/переименованном названии. CREATED отображается отдельно от перемещения, RETURNED сохраняет замечания в истории.

### Права просмотра проекта и его задач различаются

Список/детали проектов доступны всем активным пользователям, но задачи/колонки проекта защищены членством либо ролью CAPTAIN. Загружать задачи всех глобальных проектов для обычного участника нельзя: один 403 блокировал бы всю доску. Клиент получает задачи только доступных проектов, остальные проекты остаются в общем списке; при открытии чужой доски показано пояснение о членстве.

### Начальный капитан

Публичный /auth/register не зарегистрирован, начального административного bootstrap endpoint нет. Первый капитан должен уже существовать в БД, подготовленный администратором. Клиент не выдаёт себе эту роль и не использует demo-аккаунты на сервере. Тестовый smoke-скрипт создаёт капитана через SQL исключительно в изолированной временной БД с проверкой метки Compose-проекта.

## Ограничения и поведение интеграции

- UUID сохраняются строками, не преобразуются в Number. Числовые ID сохранены только для совместимости mock-режима. В карточках показывается короткая подпись UUID, в API/ссылках — полный ID.
- Токены остаются только в sessionStorage; Redux содержит профиль и роль, без пароля/access/refresh. Старый mock-профиль не открывает реальную сессию.
- После перезагрузки выполняются refresh и /me; проверяется совпадение user ID. Ротация меняет оба токена, параллельные 401 используют один refresh, повтор ограничен одним.
- После выхода очищаются бизнес-срезы Redux; ответы прежнего аккаунта после смены сессии отклоняются. Сетевая ошибка не включает моки.
- Фото и файлы требуют Bearer: фотографии читаются через защищённый Axios-запрос и Blob URL, без токена в URL. После удаления/замены UI обновляется без перезагрузки, Blob URL освобождается.
- Backend ограничивает вложение 10 МБ, аватар 5 МБ. До сохранения формы выбранный файл временно находится в памяти вкладки; после получения ID задачи/проекта загружается multipart.
- Создание родителя и загрузка файлов не атомарны. При сбое загрузки запись может уже существовать. Ошибка прямо сообщает об этом и предлагает открыть созданную запись/источники; повторное создание может дать дубликат. Общей транзакции или idempotency key в контракте нет.
- Для комментариев/вложений/истории нужны детали каждой задачи: общего агрегированного ответа нет. Клиент ограничивает параллельность шестью запросами, но число запросов растёт с размером доски. Для большого архива желательно отдельно подключить серверную фильтрацию/пагинацию.
- Недоступность источника пар не скрывает командные события; UI показывает UNAVAILABLE/CACHED. В изолированном стеке внешняя синхронизация пар не настроена, проверено пустое/недоступное состояние, не корректность расписания УУНиТ.
- Базовые типы событий общие и неизменяемые через текущий личный API; пользователь создаёт/меняет/удаляет свои типы. Это отличается от прежних локальных «типов сайта».
- При выборе «Все проекты» видны только задачи, которые разрешает backend. Авторство комментариев/результатов задаёт сервер, не текст автора из UI.

## Проверки

- **120 тестов** в 15 файлах: DTO camelCase, реальный профиль/роль, UUID, ротация и ошибки, параллельные 401, изоляция сессий, контекстная загрузка файлов, доступ к проектам, история с названиями колонок, уведомления и mock-регрессии. Дополнительно проверены UUID при переназначении задачи, снятие назначения, включение создателя проекта в members и передача параметров расписания с обработкой серверного 500.
- TypeScript/Vite production-сборка успешна. Линтер — без предупреждений.
- Поднят неизменённый backend исходного коммита с отдельными PostgreSQL и MinIO в tmpfs через client/scripts/backend-check.compose.yaml. Основная БД не использовалась.
- Raw HTTP smoke: капитан/участник, создание аккаунта/проекта/членства, задача, исходник, результат, комментарий, проверка/возврат/замечания/завершение, архив, скачивание MinIO, тип события, личное напоминание, список/прочтение уведомлений.
- В браузере с реальными Axios-запросами: создание задачи с UUID исполнителя и файлом; участник берёт и сдаёт; капитан возвращает с замечаниями; исходники сохраняются. Проверены чтение источника, загрузка/отображение/удаление аватара, приватность, серверный тип события, создание события, read-all. Интерфейс проверен на desktop и mobile.
- Подтверждены фактические 404 logout/change-password и сохранение refresh после неуспешного серверного выхода. Отзыв сессии через эти перекрытые handlers **не заявляется работающим**.
- Внешний production-сервер, CI/CD и Android FCM в этой задаче не проверялись и не менялись.
- Отдельно проверен mock-режим в браузере: вход и полная доска работают. Тестовый стек, временные реквизиты, браузер и Vite-процессы после проверок удалены/остановлены.
