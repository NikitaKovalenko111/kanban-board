Проверено 4 ноября 2026 года, исходный коммит `bd25ae5`.

Изменены только `client/` и этот отчёт в корневом `docs/`, согласно уточнению пользователя. Backend, mobile, корневой Compose и CI/CD не менялись.

## Реальные HTTP-маршруты

Источники: [роутеры](../backend/internal/transport/http/http.go), [auth handlers](../backend/internal/transport/http/handlers/auth/handler.go), [DTO](../backend/internal/transport/http/handlers/auth/dto.go), [health](../backend/internal/transport/http/handlers/system/handler.go).

У backend нет префикса `/api`: Nginx/Vite удаляет его перед передачей запроса.

| Маршрут backend | Контракт | Frontend |
|---|---|---|
| `POST /auth/login` | `{login, password}` → `200 {user_id, access_token, refresh_token, token_type}` | Подключён к форме входа. Пробелы вокруг логина убираются, пароль не изменяется |
| `POST /auth/refresh` | `{refresh_token}` → та же структура, оба токена заменяются | Восстановление после перезагрузки; обновление после 401; одна ротация для параллельных запросов |
| `POST /auth/logout` | `{refresh_token}` → `204`, пустое тело | Подключён к выходу, серверный отзыв и локальная очистка |
| `POST /auth/register` | `{username, email, password, group_name}` → `201 {user_id, message}` | UI регистрации отсутствует: несовпадения описаны ниже. Маршрут проверен smoke-скриптом на отдельной БД |
| `GET /system/health` | `200`, пустое тело | Реализован в API-клиенте и сквозных проверках |

Ошибка сервера: `{error, message}`. Известные коды (`invalid_credentials`, `invalid_refresh_token`, `invalid_request`, `request_timeout` и др.) переведены в русские сообщения. Обрабатываются таймаут, отсутствие сети, 404/405 и 5xx.

JWT middleware существует, но бизнес-маршруты с его использованием не зарегистрированы. Bearer/401/retry проверены контрактными unit-тестами с синтетическими защищёнными запросами; такие тесты не означают, что соответствующие маршруты появились на сервере.

## Что подключено и как разделены режимы

- Серверный режим включён по умолчанию: `VITE_API_MODE=backend`, `VITE_API_URL=/api`. Vite proxy использует `API_PROXY_TARGET`; production Nginx уже имеет нужное правило.
- Токены хранятся в sessionStorage, отдельно от mock-session в localStorage. В Redux находятся только строковый UUID и логин, введённый при входе. Токенов и пароля в Redux нет.
- Сохранённый mock-профиль не открывает серверный режим. При перезагрузке сессия подтверждается реальным refresh-запросом. Некорректные DTO и подмена user_id отклоняются.
- Ротация заменяет оба токена; параллельные 401 объединяются. Запрос повторяется максимум один раз. Истёкший refresh и повторный 401 возвращают к входу; сетевая ошибка не уничтожает сохранённую сессию сама по себе.
- Выход использует актуальный refresh, включая закончившуюся параллельную ротацию. Если сервер недоступен, локальные токены удаляются и интерфейс сообщает, что серверный выход не подтверждён.
- В серверном режиме неподключённые разделы показывают состояние недоступности. Демо-задачи, вымышленные роли и ложное успешное сохранение не используются. Локальный выбор светлой/тёмной темы сохранён.
- Полный демонстрационный frontend доступен отдельно с `VITE_API_MODE=mock`. Автоматического перехода на моки при ошибках backend нет.

## Функции frontend без HTTP API backend

Наличие таблиц и репозиториев не означает наличие HTTP API. На реальном сервере контрольные GET `/tasks`, `/projects`, `/team`, `/schedule/all` вернули **404**.

| Frontend | Что нельзя подключить к текущему серверу |
|---|---|
| Kanban | Список/создание/редактирование задач, четыре статуса, взятие в работу, назначение исполнителя, серверный поиск |
| Проверка результата | Загрузка решения, сдача, принятие, возврат на доработку; проверка прав исполнителя/тимлида на сервере |
| Комментарии и история | Чтение/добавление комментариев, история статусов и назначений, замечания |
| Архив | Завершённые задачи, последние пять на доске, период/поиск/фильтры, точное время завершения |
| Проекты | Список, создание, изменение, участники и функциональные роли, переключение контекста |
| Файлы | Upload/download/delete исходников, результатов и источников проекта; Attachment API отсутствует |
| Участники и доступ | Список, добавление аккаунта капитаном, капитанская роль, блокировка/восстановление, временные пароли |
| Профиль | Собственный/чужой профиль, имя, роль, аватар и его изменение, статистика задач |
| Пароль | Смена собственного пароля с проверкой текущего и административный сброс |
| Расписание | События, общее расписание проектов, расписания участников, категории, группы, окончания, поиск/фильтры |
| Типы событий и напоминания | Серверное хранение названия/цвета/одного произвольного интервала, наследование и индивидуальное переопределение |
| Приватность | Хранение и серверное применение hidden/busy/title/details для личных событий |
| Уведомления | Серверный список, прочтение, push и подписка на изменения |

Придуманные URL из прежнего mock API не отправляются в настоящий backend. Его неподдерживаемые операции также заблокированы единым API-слоем, даже если их вызовет отдельный компонент.

## Возможности и модели backend, отсутствующие или отличающиеся во frontend

1. **Публичная регистрация.** Backend не проверяет роль капитана и требует email и group_name. Frontend согласован на логин без email и создание аккаунтов капитаном; его форма задаёт также имя, должность, роль и роли проектов, которых RegisterRequest не принимает. Вызов register не выдаётся за административное создание участника; фиктивные email не генерируются. Нужен согласованный контракт, поэтому самостоятельная регистрация в UI не добавлена.
2. **Валидация регистрации.** Username: 3–32 символа `[a-z0-9._-]`; email обязателен; пароль: 8–72 байта, буква и цифра, без пробелов; группа: 2–100 символов. Контракт mock-формы другой. Ошибки валидации в текущем handler возвращаются как `500 registration_failed`, а не отдельные 4xx; backend не исправлялся.
3. **UUID.** Backend использует UUID пользователей, команд, проектов, досок, колонок, задач и файлов. Mock frontend использует числовые ID пользователей/задач/событий и строковые ID проектов. Реальная авторизация сохраняет UUID строкой в отдельной модели, без преобразования в число. Модели неподключённых сущностей пока остаются mock-моделями.
4. **Профиль и роль не возвращаются.** Login/refresh не содержат имени, username, группы, аватара или роли; GET профиля отсутствует. Введённый логин отмечен как «Логин при входе», а не полученное имя. Клиент не присваивает вымышленную роль member/lead. Регистрация сама по себе не назначает членство/роль в команде.
5. **Несколько команд в схеме БД.** Backend хранит teams/team_members с ролью внутри команды, frontend предполагает одну общую команду и проектные роли. HTTP-операций выбора/создания команд нет: это несовпадение схем, а не готовая серверная функция.
6. **Доски и произвольные колонки в БД.** Backend хранит отдельные boards и board_columns с position; frontend имеет фиксированные waiting/working/checking/done. Без бизнес-API и правил соответствия подключить это нельзя.
7. **Поля задач.** Backend хранит priority, position, created_by_user_id, updated_at, due_date, column_id; frontend не имеет управления приоритетом и произвольного порядка/набора колонок. В текущей схеме нет completed_at, истории переходов, замечаний и разделения файлов на ТЗ/результаты.
8. **Несколько исполнителей в БД.** task_assignees допускает несколько пользователей, frontend согласован на одного исполнителя. HTTP API назначения отсутствует.
9. **Файлы только к задаче в БД.** attachments содержит task_id, storage_key, mime_type и размер. Нет источников проекта и файлового HTTP API. Storage_key не интерпретируется клиентом как URL скачивания.
10. **Учебные группы.** Backend хранит свободную строку group_name у пользователя; frontend имеет фильтры 203/204/both для событий. Серверных правил расписания и привязки событий к группе нет.

Источники: [таблицы](../backend/internal/models/tables.go), [модели](../backend/internal/models/repo_models.go), [валидация](../backend/internal/services/auth/validation.go). Перечень фиксирует состояние, не меняет backend.

## Ограничение корневого Compose

Корневой compose.yaml не передаёт обязательные jwt_access_secret, jwt_refresh_secret, access_token_ttl, refresh_token_ttl, session_cleanup_interval. Backend Dockerfile не копирует тестовый YAML в runtime. Поэтому текущий корневой Compose без внешнего дополнения этих параметров не обеспечивает работающий сервер авторизации. Корневой .env сам по себе не передаёт произвольные переменные внутрь контейнера: нужны environment/env_file.

Корневой Compose не менялся. Для проверки добавлен client/scripts/backend-check.compose.yaml: локальный порт 13005, отдельные случайные секреты, PostgreSQL в tmpfs, без основного тома БД. Это тестовое окружение, не изменение production deployment.

- Unit/компонентные тесты: **100 прошли**, включая новые контракты, ошибки, ротацию, параллельные 401, истечение сессии, изоляцию mock-данных и UI входа/выхода.

- Неизменённый backend собран из текущих исходников и запущен с отдельной БД, HTTP health подтверждён.
- Smoke: register → неверный пароль 401 → login → refresh → старый refresh 401 → logout 204 → отозванный refresh 401. Контрольные бизнес-маршруты: 404.
- Браузер с реальным Vite proxy/backend: ошибка и успешный вход, UUID, отсутствие mock-реквизитов/задач/ролей, ротация на перезагрузке, desktop 1440 px и mobile 390 px, выход с реальным отзывом. В сетевом журнале — только существующие auth-маршруты.
- Явный mock-режим отдельно проверен в браузере: вход капитаном и отображение полной Kanban-доски работают.
- После проверок временный браузер, Vite-процессы и тестовые контейнеры остановлены, временные реквизиты удалены. Основная БД не использовалась.
- Полную Kanban/проектную/файловую интеграцию и реальные роли проверить нельзя: API и передача ролей отсутствуют. Внешний сервер и deployment не менялись.
