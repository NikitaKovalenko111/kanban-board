# Интеграция frontend и backend

Актуально на **7 ноября 2026 года**. Ветка: `frontend-backend-integration`. Проверен backend коммита `319a4d0` без изменения его исходников.

Изменены только `client/` и этот документ в корневом `docs/`. Рабочая БД, backend, mobile, основной Compose и CI/CD не менялись. Проверки выполнены с отдельными временными PostgreSQL и MinIO.

## Результат повторной интеграции

Прежние ошибки `GET /events → 500`, `POST /auth/logout → 404` и `POST /auth/change-password → 404` **исправлены в backend и больше не воспроизводятся**. Сценарии с текущим сервером проходят под капитаном и участником.

Клиент приведён к обновлённому контракту:

- `Project.canViewBoard` определяет доступ вместо эвристики по роли и локальному списку участников. Недоступные проекты остаются видны по названию; кнопок просмотра содержимого нет. Прямое открытие раздела показывает пояснение. Клиент не загружает их детали, колонки и задачи.
- Доска ожидает четыре уникальные колонки `BACKLOG / IN_PROGRESS / REVIEW / DONE`. Переходы используют их серверные UUID и `kind`; динамические колонки не поддерживаются, вызовов удалённого `PUT /projects/:id/columns` нет.
- Счётчики собственного профиля используют агрегирующий `GET /tasks`. Полная доска и общий архив продолжают получать все задачи доступных проектов через `GET /projects/:id/tasks`; личный endpoint не подменяет общую доску.
- Уведомления поддерживают необязательные `taskId / eventId / lessonId` и `kind=LESSON`. Ссылка на задачу отдельно загружает её детали и выбирает правильный проект. Ссылка на событие открывает его дату, а для чужого личного события — расписание владельца с серверной приватностью.
- Запрос событий использует `personId / from / to`, без устаревшего `groups`. `masked` и `partial` сохраняются; скрытые события не восстанавливаются из локальных данных.
- В источниках проекта подключены добавление HTTP(S)-ссылок в отдельном окне, их открытие и удаление. Файлы загружаются в MinIO и скачиваются с Bearer.
- Все интервалы напоминаний сохраняются и редактируются, без обрезки до первого. Для backend допустимы уникальные целые значения **1–40320 минут**.
- При выходе с истёкшим access-токеном клиент обновляет пару и отзывает актуальный refresh-токен. При недоступности сервера локальный выход завершается с честным сообщением об ошибке серверного отзыва.
- При повторе сдачи после неуспешного перехода уже загруженный результат не отправляется повторно в пределах текущей сессии вкладки.
- Создатель нового проекта входит в `members` как тимлид проекта; профильные роли обновляются с сервера. UUID исполнителя передаётся строкой, снятие назначения — `null`. В выборе исполнителя доступны активные участники проекта.

Источники контракта: [API](../backend/docs/API.md), [OpenAPI](../backend/docs/openapi.yaml), [обновления backend](../backend/docs/FRONTEND_INTEGRATION_CHANGES.md). При расхождении документации проверялось фактическое поведение HTTP и обработчиков.

## Подключённые операции

| Раздел | API и поведение |
|---|---|
| Авторизация | `POST /auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/change-password`; реальный профиль из `GET /me` |
| Профиль | Приватность через `PATCH /me`, фото через `PUT/DELETE /me/photo`, защищённое чтение `GET /users/:id/photo` |
| Участники | `GET /team` — описание приложения; `GET/POST /users`, блокировка и восстановление `PATCH /users/:id/status`, `POST /users/:id/reset-password` |
| Проекты | `GET/POST /projects`, `PATCH /projects/:id` для описания и полного состава `members`; права из `canViewBoard` |
| Источники | `POST /projects/:id/sources/files`, `/sources/links`, `DELETE /projects/:id/sources/:sourceId`, `GET /files/:id` |
| Задачи | Колонки и задачи проекта, создание задачи, детали, назначение исполнителя, `take`, явное `assign-to-me` капитаном, `move`, комментарии, исходники и результаты |
| Доработка | Переход из REVIEW/DONE обратно в IN_PROGRESS с замечанием; сервер сохраняет комментарий, историю и исходные материалы |
| Личные счётчики | `GET /tasks` — только назначенные текущему пользователю, включая завершённые |
| История | Завершённые задачи из доступных досок, локальный поиск и фильтры по исполнителю/периоду; точные `completedAt` |
| Расписание | `GET /events`, `GET /events/:id`, `POST /events`, `GET /student-groups`, `GET /schedule/lessons` |
| Типы и напоминания | `GET/POST/PATCH/DELETE /event-types`, `GET /me/reminders`, `PUT /me/reminders/:itemKey` |
| Уведомления | `GET /notifications?limit=100`, явное `POST /notifications/read-all`; обновление каждые 30 секунд и при возврате фокуса |

База API — `/api/v1`. UUID остаются строками, записи времени отправляются RFC3339, запросы защищены Bearer. Ошибки не подменяются моками. Секреты сессии находятся в sessionStorage, пароль и токены не попадают в Redux.

## Оставшиеся расхождения и ограничения backend

### 1. ID занятия в уведомлении не совпадает с ID расписания — подтверждено HTTP

При наличии внешнего идентификатора:

- `GET /notifications` возвращает `lessonId = lessons.lesson_id`, внутренний UUID;
- `GET /schedule/lessons` возвращает `lessons[].id = COALESCE(external_id, lesson_id::text)`;
- маршрута получения занятия по внутреннему UUID нет.

Это подтверждено временной записью занятия с различными UUID и `external_id`, а не предположением по названию поля. REST-уведомление содержит ровно один целевой ID, но его нельзя сопоставить с обычным синхронизированным занятием.

Клиент обрабатывает LESSON, загружает расписание своей группы в диапазоне времени доставки плюс допустимый интервал напоминания и ищет точное совпадение ID. Когда идентификаторы совпадают, открывается дата занятия. При несовпадении показывается «Занятие не найдено в текущем расписании»; чужая пара и дата доставки вместо даты занятия не подставляются. Такое же поведение проверено в браузере.

**Для полного перехода из уведомления требуется backend-контракт:** возвращать общий ID в обоих ответах, либо добавить в расписание отдельный внутренний ID, либо endpoint получения занятия по UUID. Поиск по названию небезопасен для повторяющихся пар и не используется.

### 2. Индивидуальное прочтение уведомления не предусмотрено сервером

Есть только `POST /notifications/read-all`; маршрута чтения одного уведомления нет.

По согласованному UX открытие списка больше не отмечает все записи прочитанными. Нажатие «Открыть» отмечает отдельную запись **локально для аккаунта в этом браузере**, кнопка «Прочитать все» выполняет серверный запрос. Индивидуальная отметка пока не синхронизируется между устройствами; для этого нужен endpoint с ID уведомления. Ошибка read-all отображается, ложный успех не показывается.

### 3. Наследование напоминаний остаётся неоднозначным

Backend по-прежнему независимо хранит исходные `event_reminders` и личные `user_reminders`. Изменение личного списка не отменяет исходный, а пустой список удаляет только личную настройку. Изменение типа не обновляет исходный снимок существующих событий. Ответ события не содержит этот снимок.

Клиент сохраняет все интервалы, показывает доступную личную настройку либо текущие значения типа и предупреждает об ограничении. Но он не может гарантировать отключение исходного уведомления, полную замену расписания напоминаний или точное восстановление исходного снимка старого события. Нужны единые правила замещения и данные в ответе API. Значение 0 «в момент начала» backend не принимает.

### 4. Групповой просмотр и календарные диапазоны

`GET /events` теперь выбирает GROUP по фактической группе пользователя из `personId`; параметр `groups` игнорируется. Для выбора группы в вебе клиент запрашивает расписание активного представителя выбранной группы, исключает PERSONAL и объединяет общие события без дублей. Пары загружаются непосредственно по выбранным группам через `/schedule/lessons`.

Если у группы нет активного пользователя в `GET /users`, запросить её GROUP-события через существующий контракт нельзя; UI сообщает об этом. Для полноценного просмотра любых групп нужен поддерживаемый сервером групповой фильтр.

Несмотря на пример RFC3339 в документе обновлений, фактический `DateRange` принимает **YYYY-MM-DD**, интерпретирует границы как UTC и включает последний день. Клиент отправляет именно такой формат; для событий включает соседние дни, затем распределяет их по локальной дате пользователя, чтобы не терять события у границы суток. У пар поля `date/start/end` не содержат часового пояса — клиент использует их как переданные сервером локальные значения.

### 5. Возможности веба, которых нет в текущем API

| Возможность | Ограничение |
|---|---|
| Проект события | У Event нет `projectId`; расписание на backend общее, переключатель проекта скрыт |
| Цвет проекта | Не хранится сервером; маркер вычисляется из UUID, выбор сохранённого цвета скрыт |
| Редактирование команды | `GET /team` информационный, `PATCH /team` нет |
| Ссылка в исходниках/результатах задачи | Вложения задачи только FILE с `kind=SOURCE/RESULT`; URL поддерживается у источников проекта, отдельного контракта для ссылок задачи нет |
| Смена логина | `PATCH /me` не принимает username/login; капитан также не имеет маршрута редактирования логина участника |
| Изменение чужой учебной группы | `PATCH /me` позволяет менять собственную группу; формы редактирования группы другого аккаунта сервером не предусмотрено |

Эти действия не имитируются локальным успешным сохранением в backend-режиме.

## Возможности backend без отдельного управления в текущем frontend

| API | Текущее состояние |
|---|---|
| `PATCH /me` для fullName/studentGroup | Данные читаются; отдельной формы редактирования этих полей в этой ветке нет |
| `PATCH /users/:id/role`, `DELETE /users/:id` | Глобальная роль задаётся при создании; изменения роли и удаления/обезличивания в UI нет |
| `DELETE /projects/:id` | Кнопки удаления проекта нет |
| `PATCH/DELETE /tasks/:id` | Назначение подключено; редактирования названия, ТЗ, срока и удаления в этой ветке нет |
| Приоритет и порядок задач | Backend поддерживает LOW/NORMAL/HIGH и position; текущий UI этой ветки создаёт NORMAL, управления приоритетом/порядком нет |
| `PATCH/DELETE /comments/:id` | Редактирование и удаление комментариев не выведены |
| `DELETE /tasks/:id/attachments/:attachmentId` | Отдельного удаления уже сохранённых вложений задачи нет |
| `GET /tasks/completed`, `GET /tasks/assigned` | Общий архив фильтруется в клиенте; персональные счётчики используют новый `GET /tasks` |
| `PATCH/DELETE /events/:id` | Создание и переход из уведомления подключены; редактирования/удаления события нет |
| SSE `/notifications/stream` | Остаётся REST polling; модель LESSON поддержана в REST, SSE не подключён |
| `/me/push-tokens`, FCM | Регистрация устройств и web push не добавлялись |

Дополнительные функции сверх существующих экранов не добавлялись автоматически. Отсутствие UI не объявляется ошибкой backend.

## Проверки и воспроизведение

- **136 unit/компонентных тестов в 17 файлах**: контракты, UUID, canViewBoard, фиксированные колонки, личный список задач, приватность, групповой запрос, все интервалы напоминаний, загрузка ссылок, повтор сдачи файла, уведомления LESSON, явное прочтение, ротация и выход.
- `npm run build` и `npm run lint` проходят.
- [backend-smoke.mjs](../client/scripts/backend-smoke.mjs) на отдельном стеке: обе роли, создание пользователя/проекта/членства, четыре колонки, назначение, исходник/результат, комментарий, возврат с замечанием, завершение и архив, настоящий контент файлов MinIO, события и четыре режима приватности, типы и напоминания, уведомления, смена пароля, ротация и отзыв refresh. Отдельно воспроизводится несовпадение ID занятия.
- [browser-check.mjs](../client/scripts/browser-check.mjs): реальные Axios-запросы, задача с UUID исполнителя и файлом, сдача и возврат, сохранение исходников, загрузка/защищённый показ/удаление аватара, настройки приватности, несколько напоминаний типа, создание события, явное read-all, создание/удаление ссылки проекта, переход к задаче и честная ошибка для несовместимого ID занятия.
- Рабочий сервер, внешняя синхронизация расписания УУНиТ, реальные push-уведомления, Safari/Firefox и сохранение файла на диск обычным браузером не проверялись. Контент скачанного Blob и HTTP-файла проверен.
- Изолированный стек не изменяет рабочую БД; временные пароли и токены не выводятся и не коммитятся.

Инструкция запуска тестового стека — [client/README.md](../client/README.md). По умолчанию клиент использует `VITE_API_MODE=backend`, база `/api/v1`. Mock-режим включается только явно и не служит запасным ответом при сбоях API.
