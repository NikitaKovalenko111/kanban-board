# Автоматический деплой

Этап 3 (сервер и GitHub Secrets) **НЕ ВЫПОЛНЕН**, пропущен по просьбе пользователя. Workflow подготовлен локально; реальный деплой пока не проверен.

## Настройки перед первым запуском

В Settings → Secrets and variables → Actions добавить repository secrets:

- `SERVER_HOST`: `94.41.18.199`.
- `SERVER_USER`: `arbusik666`.
- `SERVER_SSH_KEY`: отдельный приватный ключ деплоя без passphrase, публичная часть которого установлена на сервере.
- `SERVER_KNOWN_HOSTS`: проверенная запись для `[94.41.18.199]:2222`.

В разделе Variables добавить `SERVER_PATH`: подтверждённый абсолютный путь к корню репозитория на сервере. Пример старого неподтверждённого пути: `/projects/kod_v_sapoge/it-project-showcase`. Workflow разрешает путь без пробелов, только латиницу, цифры, `_`, `.`, `/`, `-`.

На сервере нужны Linux, Bash, Git, `flock`, Docker и Compose с `--wait`. Пользователь деплоя должен иметь права на каталог и Docker. В каталоге должен быть клон именно этого GitHub-репозитория, чистая рабочая копия и игнорируемый Git файл `.env` с паролем PostgreSQL. Первоначально получить main с файлами Docker и `.gitignore`, затем создать `.env`. Доступ сервера к origin на чтение настраивается отдельно.

## Что делает CD

1. Запускается после успешного CI для push в main этого же репозитория.
2. Проверяет наличие настроек и формат адреса, пользователя, пути и SHA. Проверяет читаемость приватного ключа и наличие записи known_hosts для порта 2222. Значения секретов не печатает.
3. Передаёт серверу `scripts/deploy.sh` через SSH с проверкой ключа хоста, неинтерактивным входом и таймаутами.
4. На сервере берёт `flock` и проверяет origin и отсутствие локальных изменений. В GitHub отдельная concurrency-группа предотвращает пересечение запусков CD; текущий деплой не отменяется новым.
5. Выполняет fetch main. Если SHA успешного CI уже не совпадает с main, пропускает этот устаревший запуск. Иначе переключает рабочую копию в detached HEAD на точный SHA.
6. Проверяет Compose и собирает образы до замены работающих контейнеров. Запускает `up --wait` и проверяет `/`, `/health`, `/api/system/health` внутри frontend. Внешняя доступность адреса сервера проверяется отдельно на этапе 5.
7. Только после успешных проверок сохраняет SHA в Git-каталоге `kanban-deploy-state/deployed.sha`, а предыдущий успешный SHA — в `previous.sha`. Выводит SHA и состояние контейнеров. Приватный ключ удаляется с runner даже при ошибке.

Workflow не перезаписывает локальные изменения и не выполняет автоматический откат БД. При провале healthcheck CD завершается ошибкой; часть контейнеров уже может быть обновлена. Пересборка обеспечивает соответствие исходного кода SHA, но базовые образы с плавающими тегами могут отличаться между сборками.

## Ручной откат

После неудачного деплоя `deployed.sha` остаётся последним успешно проверенным SHA. Для отмены последнего *успешного* деплоя использовать `previous.sha`. При первом деплое проверенной предыдущей версии может не быть — потребуется отдельно выбрать и проверить коммит.

На сервере из корня проекта выполнить (заменить путь, SHA и имя выбранного файла состояния по ситуации):

```bash
cd /confirmed/project/path
bash
set -euo pipefail
exec 9> "$(git rev-parse --git-path kanban-deploy.lock)"
flock -n 9
state_dir=$(git rev-parse --git-path kanban-deploy-state)
target=$(cat "$state_dir/deployed.sha")
[[ "$target" =~ ^[a-f0-9]{40}$ ]]
test -z "$(git status --porcelain)"
git cat-file -e "$target^{commit}"
git checkout --detach "$target"
docker compose config --quiet
docker compose build
docker compose up -d --remove-orphans --wait --wait-timeout 180
docker compose exec -T frontend wget -q -O /dev/null http://127.0.0.1/health
docker compose exec -T frontend wget -q -O /dev/null http://127.0.0.1/api/system/health
printf '%s\n' "$target" > "$state_dir/deployed.sha.tmp"
mv "$state_dir/deployed.sha.tmp" "$state_dir/deployed.sha"
docker compose ps
exit
```

Сохранить прежние SHA перед ручным откатом в журнале администратора. Том PostgreSQL не удалять. Изменения схемы/данных БД могут быть несовместимы со старым кодом; перед будущими миграциями нужен отдельный план резервного копирования и восстановления.

## Локальная проверка без сервера

```bash
bash -n scripts/deploy.sh
bash scripts/test-deploy.sh
```

Тест подменяет внешние команды Git/Docker/flock и проверяет ветвления сценария: успешное сохранение SHA, пропуск старого CI, отказ при изменённой рабочей копии, неправильном origin или занятой блокировке, отказ сборки до замены контейнеров и несохранение успеха при ошибке healthcheck. Реальные SSH, блокировка ОС, GitHub Actions и Docker этим тестом не проверяются.

Локальный результат: проверка синтаксиса Bash и все семь сценариев теста прошли успешно. Workflow проверен `actionlint`, оба скрипта — `ShellCheck` без замечаний после исправлений. `git diff --check` прошёл. Для shell-скриптов задан LF в `.gitattributes`.

До завершения этапа 3 не запускать проверку деплоя push в main. Реальный полный прогон и откат остаются задачами этапа 5.
