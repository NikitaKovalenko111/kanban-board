# Документация разработчика мобильного приложения

## 1. Назначение

`mobile/` — Android-клиент Kanban Board. Спринт 2 добавляет проекты в нижнюю навигацию, аудит задач, расширенные события и сетевой слой с JWT. Без параметра адреса API приложение использует локальные демонстрационные данные.

Технологии:

- Kotlin;
- Jetpack Compose + Material 3;
- Navigation Compose;
- Android ViewModel;
- Gradle Kotlin DSL;
- минимальная версия Android — API 26;
- compile/target SDK — API 37;
- JDK 17.

## 2. Структура

```text
mobile/
├── app/src/main/java/com/kanbanboard/mobile/
│   ├── MainActivity.kt           # точка входа Android
│   ├── data/
│   │   ├── KanbanRepository.kt   # контракт данных и mock-реализация
│   │   ├── AppStorage.kt         # настройки и пользовательские события
│   │   └── ReminderScheduler.kt  # локальные Android-уведомления
│   ├── model/
│   │   └── Models.kt             # модели предметной области
│   └── ui/
│       ├── AppViewModel.kt       # состояние и действия пользователя
│       ├── KanbanApp.kt          # навигация и экраны
│       ├── ScheduleUi.kt         # единая лента, создание события, настройки
│       └── theme/Theme.kt        # дизайн-токены приложения
└── app/src/test/                 # локальные unit-тесты
```

Направление зависимостей: `UI -> ViewModel -> FakeKanbanRepository` в демонстрационном режиме или `UI -> ViewModel -> RemoteWorkspaceGateway -> BackendApi` в сетевом. UI не должен напрямую обращаться к сети или базе данных.

## 3. Экраны и сценарии

### Вход

Экран повторяет веб-клиент: логин и пароль, выданные тимлидом. Mock-аккаунты: `alexey / lead123` для тимлида и `maria / member123` для участника. После подключения backend метод `KanbanRepository.login` должен возвращать профиль сервера или ошибку авторизации.

### Доска

Поддерживаются статусы `WAITING`, `WORKING`, `CHECKING`, `DONE`. Переход вперёд выполняется из деталей задачи. При подключении backend мутация должна отправляться на сервер, а локальное состояние — обновляться после успешного ответа.

На доске сначала выбирается команда, затем один из её проектов; карточки фильтруются по `projectId`. При смене команды активируется её первый проект. Пока список проектов и задачи демонстрационные. Сервер должен возвращать проекты только выбранной команды и доску выбранного проекта.

Права переходов:

- назначенный исполнитель: `WAITING -> WORKING -> CHECKING`;
- тимлид: `CHECKING -> DONE`, `CHECKING -> WORKING`, `DONE -> WORKING`;
- остальные пользователи не могут изменить статус чужой задачи.

Эта проверка реализована в UI и `AppViewModel`, но является только защитой интерфейса. Backend обязан повторно проверять пользователя, команду, назначение задачи и допустимость перехода; запрос от клиента нельзя считать доверенным.

### Детали задачи

Отображаются описание, исполнитель, дедлайн, исходные файлы и комментарии. Сейчас добавление комментария и смена статуса живут только в памяти процесса.

### История задач

Показывает выполненные задачи, результат работы, дату завершения и исполнителя. Доступны поиск, фильтрация по участнику и периоды: всё время, 7 дней, 30 дней.

### Участники и управление командой

Список участников и публичный профиль доступны всей команде. Профиль показывает роль, статус доступа и статистику задач. Тимлид дополнительно может открыть управление командой, изменить её описание, создать mock-аккаунт с временным паролем и заблокировать или восстановить участника.

### Команды

Из профиля открывается список команд. Пользователь может открыть карточку команды, вступить в доступную команду, выбрать одну из своих команд как рабочую и выйти из команды. Выбранная команда определяет задачи, историю и состав участников на основных экранах.

В mock-слое членство хранится только в памяти. Backend должен проверять право видеть закрытую команду и выполнять операции вступления/выхода транзакционно.

### Профиль и настройки

Профиль содержит данные пользователя и статистику. Из него открываются настройки: светлая/тёмная тема и учебная группа 203/204. Эти настройки сохраняются в `SharedPreferences` и восстанавливаются после перезапуска. Экран настроек не обращается к сети.

### Расписание

Расписание — вторая вкладка нижней панели. Единая хронологическая лента включает пары выбранной группы, события и дедлайны активных задач выбранной команды. Лекции, практики и лабораторные выделены разными цветами. Фильтр по охвату показывает командные, групповые или личные записи. Пары пока берутся из `FakeKanbanRepository`, а не из ИСУ; это демонстрационные данные на текущий день. В production репозиторий должен:

1. запросить свежие данные;
2. сохранить их локально;
3. при ошибке сети вернуть последний кеш с отметкой времени обновления.

### События и напоминания

Событие создаётся с датой, временем, охватом (команда, выбранная группа, лично), типом и несколькими интервалами напоминаний. Есть базовые и пользовательские типы; для пользовательского типа выбираются цвет и интервалы напоминаний по умолчанию. Их можно изменить для конкретного события. События и пользовательские типы сохраняются в `SharedPreferences`. Личные события видны только создателю, групповые — пользователям выбранной группы, командные — выбранной команде. Пока это локальная фильтрация: для реального многопользовательского доступа и проверки прав требуется backend.

Форма события отдельно выбирает время начала и окончания (окончание должно быть позже начала) и принимает необязательное описание. Нажатие на событие в ленте открывает детали с полным описанием. Поля `endTime` и `description` сохраняются вместе с событием; старые локальные записи без этих полей читаются со значениями по умолчанию.

Напоминания планируются через `AlarmManager.setAndAllowWhileIdle` и показываются как системные локальные уведомления. На Android 13+ при создании события с напоминанием запрашивается разрешение уведомлений. После перезагрузки устройства сохранённые напоминания планируются заново. Время срабатывания может быть неточным из-за ограничений энергосбережения Android. Это локальные уведомления устройства, не удалённые push через FCM; для FCM необходим серверный контракт и инфраструктура доставки.

Для синхронизации между людьми нужен сервер как единый источник событий: `POST /events` сохраняет событие и его охват, `GET /events?teamId=...&group=...` возвращает доступные пользователю командные, групповые и личные события. Сервер обязан проверять членство в команде, группу и владельца личного события. Клиент должен обновлять ленту после записи и при открытии расписания, а затем кешировать полученные данные для офлайн-доступа. Сейчас `AppViewModel.createEvent` записывает только в `SharedPreferences`; другие устройства этих событий не видят. Прямая пересылка между телефонами не предусмотрена.

### Навигация

Нижняя панель: `Доска`, `Расписание`, `Проекты`, `История`, `Профиль`. Участники перенесены в профиль. Иконки взяты из одного набора Material и имеют одинаковый размер 24 dp. Переходы между вложенными экранами используют горизонтальный слайд; обратный переход — слайд в противоположную сторону. Системный жест назад обрабатывается `Navigation Compose`; Android 13+ использует Predictive Back при поддержке устройства и включённой системной анимации.

Карточки и имена участников на доске, в истории, задаче и команде открывают профиль участника. Переход выполняется поверх текущего маршрута; системный жест или кнопка «Назад» возвращает к тому же экрану (в том числе к деталям выбранной команды), не сбрасывая выбор.

Каждый маршрут `NavHost` помещён в `DestinationSurface`, который скругляет непосредственно анимируемое содержимое по радиусам устройства. Это устраняет прямоугольные края при возврате между экранами; общий контейнер `DeviceRoundedSurface` сохраняет скругление в обычном состоянии. Анимацию возврата с корневого экрана на рабочий стол выполняют Android и launcher, она не управляется этими контейнерами.

На Android 12+ корневое содержимое получает радиусы углов из `WindowInsets.getRoundedCorner`; при отсутствии данных используется запасной радиус 20 dp. Это сглаживает силуэт экрана при системной анимации возврата. Масштабирование и момент закрытия окна остаются под управлением Android и зависят от версии ОС/лаунчера.

## 4. Соответствие дизайну веб-клиента

Мобильная тема повторяет токены ветки `frontend-new-design`:

| Токен | Значение | Назначение |
|---|---:|---|
| Background | `#F5F7FB` | фон экранов |
| Surface | `#FFFFFF` | карточки и навигация |
| Text | `#20242C` | основной текст |
| Muted | `#77808F` | вторичный текст |
| Primary | `#6576DF` | основные действия и активные состояния |
| Border | `#E5E9F0` | границы |
| Danger | `#C65F68` | ошибки и опасные действия |

Основные карточки имеют радиус 14 dp, крупные контейнеры — 22 dp. Новые компоненты должны использовать цвета из `ui/theme/Theme.kt`, а не объявлять отдельные основные цвета внутри экранов.

## 5. Подключение backend

Подробный перечень нужных Android-клиенту HTTP-запросов, полей, примеров и открытых вопросов: [mobile/BACKEND_API_CONTRACT.md](mobile/BACKEND_API_CONTRACT.md). Это проект контракта для согласования, а не подтверждённые маршруты сервера.

Актуальные запросы Спринта 2, включая JWT, аудит и проекты: [mobile/API_REQUESTS_SPRINT2.md](mobile/API_REQUESTS_SPRINT2.md). `BackendApi.kt` и `RemoteWorkspaceGateway` включаются только при заданном `-PkanbanApiBaseUrl=https://.../`. Токен хранится в памяти процесса и передаётся в заголовке `Authorization: Bearer`; проверка JWT и прав всегда выполняется сервером. До появления серверного OpenAPI соответствие DTO и маршрутов остаётся неподтверждённым.

`BackendApi.kt` содержит Retrofit-маршруты, DTO и Bearer-интерцептор; `RemoteWorkspaceGateway` преобразует ответы в UI-модели. `AppViewModel` включает этот путь только при заданном HTTPS URL. В mock-режиме вход и данные остаются локальными. В сетевом режиме авторизация и загрузка данных выполняются асинхронно; токен хранится только в памяти. При `401` пользователь возвращается к экрану входа. Кеш пар по группе хранится в `SharedPreferences` для fallback.

Дальнейший порядок: получить серверный OpenAPI, сверить каждый DTO и endpoint с фактическими ответами, провести сквозные проверки под Team Lead и Member, проверить реальную загрузку/скачивание файлов и синхронизацию событий на двух устройствах. Пока серверного кода нет в `develop`, ни эти сценарии, ни серверная проверка JWT не подтверждены. Перечень запросов для бэка находится в `mobile/API_REQUESTS_SPRINT2.md`.

## 6. Проверки перед Pull Request

```powershell
cd mobile
.\gradlew.bat test assembleDebug
```

Дополнительно вручную проверить:

- неверная пара логин/пароль показывает ошибку;
- `alexey / lead123` открывает функции тимлида;
- `maria / member123` открывает функции участника без управления командой;
- фильтры статусов показывают правильные карточки;
- история показывает только выполненные задачи;
- открываются список участников и профиль участника;
- тимлид может открыть управление командой и создать задачу;
- чужой исполнитель не может изменить статус задачи;
- дедлайн выбирается через календарь;
- история фильтруется по периоду;
- рабочую команду можно сменить, а из команды можно выйти;
- статус задачи изменяется;
- новый комментарий появляется в списке;
- переключаются группы 203/204 и обновляется единая лента;
- создаются личное, групповое и командное события;
- создаётся пользовательский тип с цветом и выбираются интервалы напоминаний;
- после перезапуска сохраняются тема, группа и созданные события;
- переход в настройки и обратно не приводит к крашу;
- системный свайп назад открывает предыдущий экран;
- выход возвращает на экран входа.

## 7. Git-процесс

- базовая ветка: `develop`;
- feature-ветки для мобильных задач имеют префикс `mobile-`;
- прямые изменения в `develop` не допускаются;
- небольшие логические изменения оформляются отдельными коммитами;
- Pull Request создаётся из feature-ветки в `develop`;
- перед слиянием обязательны сборка, тесты и review другим участником.
