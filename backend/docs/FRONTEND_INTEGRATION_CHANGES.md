# Изменения backend для интеграции с frontend

Актуально на **8 ноября 2026 года**.

Документ описывает, что уже исправлено в backend после проверки `docs/FRONTEND_BACKEND_INTEGRATION.md` и какие изменения остаются на стороне frontend. Frontend не считается устаревшим: это отдельный клиент с некоторыми отличиями от мобильного приложения.

Основной контракт находится в [API.md](API.md), машиночитаемое описание — в [openapi.yaml](openapi.yaml).

## Исправлено в backend

### События и просмотр чужого расписания

Исправлен `GET /api/v1/events`: из SQL убран неиспользуемый параметр, из-за которого PostgreSQL возвращал `SQLSTATE 42P18` и HTTP `500`.

Запрос расписания другого пользователя:

```http
GET /api/v1/events?personId=<userId>&from=2026-11-02T00:00:00%2B05:00&to=2026-11-09T00:00:00%2B05:00 HTTP/1.1
Authorization: Bearer <accessToken>
```

Правила ответа:

- `personId` — пользователь, чьё расписание нужно получить; без него используется текущий пользователь;
- `TEAM`-события видны всем активным пользователям;
- `GROUP`-события выбираются по фактической учебной группе пользователя из `personId`;
- его `PERSONAL`-события возвращаются с учётом `schedulePrivacy`;
- при `NOTHING` чужое личное событие не передаётся вообще;
- при `BUSY`, `TITLE` и `TITLE_AND_DESCRIPTION` backend скрывает соответствующие поля и выставляет `masked`/`partial`;
- параметр `groups` оставлен для совместимости, но больше не используется.

Те же ограничения применяются к `GET /api/v1/events/{eventId}`.

### Проекты без доступа к доске

`GET /api/v1/projects` возвращает все проекты, но не раскрывает детали недоступных проектов.

Проект без доступа:

```json
{
  "id": "b760844c-8a2e-4c67-bfd8-07c35dceee96",
  "name": "Мобильное приложение",
  "canViewBoard": false
}
```

Доступный проект:

```json
{
  "id": "a3cc3caf-cce8-4f85-b641-867a40ce959e",
  "name": "Kanban Board",
  "description": "Разработка системы",
  "canViewBoard": true,
  "members": [],
  "sources": []
}
```

Если `canViewBoard=false`, поля `description`, `members` и `sources` не отправляются. Прямой `GET /api/v1/projects/{projectId}`, запрос колонок и запрос задач такого проекта не дают доступ к содержимому доски.

### Все задачи текущего пользователя

Добавлен отдельный агрегирующий маршрут:

```http
GET /api/v1/tasks HTTP/1.1
Authorization: Bearer <accessToken>
```

Он возвращает назначенные текущему пользователю задачи из всех проектов, включая выполненные. Маршрут не заменяет `GET /projects/{projectId}/tasks`, который нужен для полной доски доступного проекта.

### Четыре фиксированные колонки

Доска теперь всегда содержит ровно четыре колонки:

| position | kind | Название |
|---:|---|---|
| 0 | `BACKLOG` | Ожидает |
| 1 | `IN_PROGRESS` | В работе |
| 2 | `REVIEW` | На проверке |
| 3 | `DONE` | Выполнено |

`PUT /api/v1/projects/{projectId}/columns` удалён из обработчиков и OpenAPI. Миграция создаёт недостающие стандартные колонки, переносит задачи из лишних колонок в соответствующую фиксированную колонку и удаляет лишние колонки.

### Единая таблица уведомлений

Уведомление связано ровно с одной сущностью:

- `taskId` — уведомление задачи;
- `eventId` — уведомление события;
- `lessonId` — уведомление занятия.

Для занятий добавлен тип `LESSON`. Не относящиеся к уведомлению идентификаторы в JSON не отправляются.

```json
{
  "id": "950e8400-e29b-41d4-a716-446655440004",
  "kind": "LESSON",
  "title": "Математический анализ",
  "text": "Занятие начнётся через 15 мин.",
  "at": "2026-11-04T18:25:00+05:00",
  "read": false,
  "lessonId": "bdb10a98-9b1f-47db-8092-e7a98248a370"
}
```

Эта же полная модель используется в REST, SSE и data payload FCM.

### Расписание УУНиТ

HTML-парсер удалён. Backend получает список групп и занятия из JSON API, используемого официальным сайтом расписания УУНиТ.

Настройки синхронизации:

```env
SCHEDULE_SYNC_ENABLED=true
SCHEDULE_SYNC_SOURCE_URL=https://dev.uust-time.ru/api/v/852972
SCHEDULE_SYNC_SEMESTER_ID=241
SCHEDULE_SYNC_SEMESTER_START=2026-09-01
SCHEDULE_SYNC_INTERVAL=6h
SCHEDULE_SYNC_HTTP_TIMEOUT=20s
```

Новый парсер и преобразование недель семестра находятся в `internal/services/schedule/sync.go`. Периодический запуск находится в `internal/services/schedule_scheduler.go`, конфигурация — в `internal/config/integrations.go`.

API расписания публично не документирован и содержит версию в URL. При смене семестра нужно проверить и обновить `source_url`, `semester_id` и `semester_start`.

### Авторизация

Защищённые auth-маршруты подключены через отдельный защищённый роутер и доступны по прежним URL:

```http
POST /api/v1/auth/logout
POST /api/v1/auth/change-password
```

`PATCH /api/v1/me` также оставлен без изменения URL.

### GET /team

`GET /team` — не список пользователей и не состав проекта. Это статическая информация о команде приложения:

```http
GET /api/v1/team HTTP/1.1
Authorization: Bearer <accessToken>
```

```json
{
  "name": "Kanban Board",
  "description": "Студенческая команда"
}
```

Для управления пользователями используются:

```http
GET    /api/v1/users?search=<строка>
POST   /api/v1/users
GET    /api/v1/users/{userId}
PATCH  /api/v1/users/{userId}/status
PATCH  /api/v1/users/{userId}/role
POST   /api/v1/users/{userId}/reset-password
DELETE /api/v1/users/{userId}
```

Состав проекта передаётся в `members` при `POST /projects` и полностью заменяется переданным списком при `PATCH /projects/{projectId}`.

## Что нужно изменить во frontend

### 1. Учитывать canViewBoard

Нужно добавить `canViewBoard: boolean` в frontend-модель проекта.

Для проекта с `canViewBoard=false` frontend не должен запрашивать:

- `GET /projects/{projectId}`;
- `GET /projects/{projectId}/columns`;
- `GET /projects/{projectId}/tasks`;
- источники или другие детали доски.

Такой проект можно показать в общем списке как недоступный. При выборе следует показать сообщение о необходимости доступа, а не пытаться загрузить доску и обрабатывать ожидаемый `403`.

Существующую клиентскую эвристику определения доступных проектов по локальному списку участников следует заменить серверным `canViewBoard`.

### 2. Удалить поддержку динамических колонок

Нужно окончательно убрать из frontend:

- редактор колонок;
- вызов `PUT /projects/{projectId}/columns`;
- объединение нескольких `IN_PROGRESS`-колонок;
- выбор «первой подходящей» динамической колонки.

Колонки следует сопоставлять по `kind`. `id`, полученный от backend, по-прежнему используется в `POST /tasks/{taskId}/move` как `columnId`.

### 3. Подключить GET /tasks

Для экранов «Мои задачи», общих счётчиков и списка задач пользователя следует использовать:

```http
GET /api/v1/tasks
```

Это устраняет необходимость загружать все проекты, затем отдельно получать задачи каждого проекта. Для полноценной канбан-доски выбранного проекта остаётся `GET /projects/{projectId}/tasks`.

Если интерфейсу нужны комментарии, история и вложения, их по-прежнему следует получать через `GET /tasks/{taskId}`.

### 4. Обновить запрос событий

Frontend может перестать передавать `groups` в `GET /events`. Достаточно:

```http
GET /api/v1/events?personId=<userId>&from=2026-11-02&to=2026-11-09
```

Нужно корректно отображать:

- отсутствие закрытых событий как нормальный результат, а не ошибку;
- `masked=true` как занятый интервал без деталей;
- `partial=true` как событие с ограниченным набором полей.

Тест, который сейчас ожидает HTTP `500` от `GET /events`, нужно заменить проверкой успешного ответа и правил приватности.

### 5. Поддержать уведомления занятий

В frontend-модель уведомления нужно добавить:

```ts
lessonId?: string
```

Также нужно добавить тип `LESSON`. При открытии такого уведомления frontend должен перейти к расписанию и дате соответствующего занятия. Нельзя предполагать, что одновременно будут присутствовать `taskId` и `eventId`: backend присылает ровно один целевой идентификатор.

`lessonId` теперь совпадает с `lessons[].id`. Для прямого перехода также доступен `GET /schedule/lessons/{lessonId}`; внешний идентификатор УУНиТ возвращается отдельно как `externalId`.

Если frontend подключает SSE, он должен использовать ту же модель уведомления, что и `GET /notifications`.

### 6. Обновить текст и логику ошибок

Старое сообщение о серверной ошибке `GET /events` больше не актуально. Также больше не нужно считать `POST /auth/logout` и `POST /auth/change-password` заведомо недоступными.

При реальной сетевой или серверной ошибке frontend по-прежнему должен показывать ошибку, а не подменять ответ пустым расписанием или локальным успешным результатом.

### 7. Обновить клиентские DTO и тестовые адаптеры

Нужно синхронизировать real API, mock API и тестовые данные:

- `Project.canViewBoard`;
- фиксированные четыре `BoardColumn.kind`;
- агрегирующий `GET /tasks`;
- `Notification.lessonId` и `kind=LESSON`;
- запрос `GET /events` без обязательного `groups`;
- отсутствие `PUT /projects/{projectId}/columns`.

Mock API может сохранять собственные числовые идентификаторы внутри mock-режима, но DTO реального backend должны использовать UUID-строки.

## Дополнительно исправлено 8 ноября

- Добавлено индивидуальное прочтение через `POST /notifications/{notificationId}/read`.
- `PUT /me/reminders/{itemKey}` теперь является явным переопределением: пустой список отключает напоминания; `DELETE` возвращает наследование исходных интервалов.
- Добавлен групповой режим `GET /events?group=...`; активный представитель группы больше не нужен.
- `PATCH /me` принимает `username`; капитан может изменить `username` и `studentGroup` через `PATCH /users/{userId}`.
- Проекты получили сохраняемое поле `color`.
- События получили необязательное поле `projectId`; оно допустимо для `TEAM`-событий доступного проекта.
- Диапазоны `from`/`to` документированы как `YYYY-MM-DD`, причём день `to` включается полностью.

## Что оставлено без изменения

- `PATCH /api/v1/me` и `POST /api/v1/auth/change-password` сохраняют текущие URL и формат.
- Проектные источники сохраняют существующие маршруты для ссылок, файлов и удаления.
- `GET /team` остаётся информационным; `PATCH /team` не добавлен.
- Для списка пользователей используется `GET /users`, для участников конкретного проекта — `Project.members`.
- Ссылки среди вложений задачи не добавлены; ссылки остаются только у источников проекта.

## Порядок обновления frontend

1. Обновить DTO проектов, уведомлений и колонок.
2. Перевести проверку доступа проекта на `canViewBoard`.
3. Удалить динамические колонки и запрос их изменения.
4. Подключить `GET /tasks` для пользовательского агрегированного списка.
5. Обновить расписание и тесты `GET /events`.
6. Добавить обработку `LESSON`/`lessonId` в REST и SSE.
7. Повторно проверить logout, смену пароля и refresh-сессию на текущем backend.
